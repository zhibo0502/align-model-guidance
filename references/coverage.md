# 覆盖率与证据

建立逐项表或需要报告覆盖率时读取。沿用项目已有格式；下列是最低语义字段，不强制新增 JSON、脚本或一整套目录。

## 先固定两个分母

- **指导范围**：实际读取的官方页面、日期/版本、选定章节。为每个独立条目保留来源定位；另列章节/段落到条目 ID 的映射。重合段落可以映射同一 ID，未读章节必须列为缺口。主文未完整取得时只报告已读范围，不能给整份指导的完成率。
- **文件范围**：项目根、基线提交、候选文件路径和明确排除项；仓库外入口单列。固定的是本次清单，不能用日后增长的 `git ls-files` 重新定义旧分母。新发现文件增补范围并解释变化；新增审计产物不作为“已检查文件”抬高完成比例。

涉及非 Git 项目时用路径清单和必要哈希固定范围。使用脚本时明确读取当前工作树还是提交对象、哈希对应哪一版本；重算写入新位置，不覆盖原证据。哈希用于追溯字节，不自动证明语义审阅。

## 条目表

| 字段 | 内容 |
|---|---|
| ID / 来源 | 独立条目编号、官方 URL 与章节/段落定位 |
| 要求 | 简短转述；标记建议、硬限制、条件能力或信息说明 |
| 适用性 | 适用、不适用、未知；项目现状和范围依据 |
| 符合性 | 已确认适用项记录符合、不符合或未知及其证据；不适用项不作符合性判定 |
| 处置 | 已符合、已修正并核验、明确例外、待处理（待查明/待整改）、未知；不适用单列 |
| 证据 | 对应文件位置、最终差异、检查结果；API 条目可引用具体调用入口 |
| 缺口 | 未完成工作或例外理由；条件能力不写“实现通过” |

不适用不是“暂时没做”。应用有证据确认适用且存在兼容问题却未修复，应是待处理（待整改）或明确例外；适用性或符合性尚未查明，应是待处理（待查明）或未知。处置标签不能替代判定证据；已修改但未核验不能计入已对齐。官方建议与用户选择不同且该建议非硬限制时，可明确保留用户选择，不称完全遵循官方建议。

## 文件清单

每项记录路径、基线/可选哈希、文件角色，以及筛查、语义审阅、修改和验证的实际状态。全文关键词筛查只标记筛查；人工或 agent 阅读并判断过实际指令才计语义审阅。自动重新运行旧清单时不能继承“已人工审阅”来声称本次又审过。

## 分开计算

- **指导判定覆盖率**＝有证据完成适用性、适用时的符合性判定并记录处置的条目数 / 官方范围内独立条目总数。有依据不适用、已判定的明确例外和待整改可计判定；例外及待整改不计对齐。适用性或符合性仍未知、待查明的不计已完成判定。
- **适用项对齐率**＝已符合或已修正且核验的适用项 / 全部已确认适用项。已确认适用的例外、待处理及符合性未知项仍在分母。分别报告适用性未知和已确认适用但符合性未知的数量；存在未知时不能称完整对齐。
- **文件筛查覆盖率**＝实际完成筛查的候选文件 / 固定候选文件清单。读取失败或未读取留在分母；排除项另报数量和理由。
- **语义审阅覆盖率**＝实际完成语义审阅的文件 / 已声明需语义审阅的文件集合。说明这只是重点集合；若声称全项目逐文件审阅，分母就必须是全部在范围内文件。

分母为零时写“不适用/无候选”，不能写 100%。每个比例同时给出整数分子、分母。不以测试数量、修改文件数量或模型回答自称替代覆盖率。范围内还有未判定项时，不用较小的已读/已选集合包装成全覆盖。

示例：12 项中，6 已符合、2 已修正并核验、2 有依据不适用、1 已判定不符合的明确例外、1 适用性未知。判定覆盖率为 11/12；已确认适用项对齐为 8/9，另有 1 项适用性未知。不能报告 100% 对齐。

只读审查示例：10 项均有证据确认适用且不符合，全部待整改，判定覆盖率为 10/10，对齐率为 0/10；将其中任一项改为明确例外，不改变这两个比例。若其中 2 项的符合性尚未查明，则判定覆盖率为 8/10，对齐率仍为 0/10，并另报 2 项符合性未知。

## 完成报告

先给结论和主要改动，再给上述数字、证据链接与未解决项。明确审阅方式（自审/独立审阅）和运行验证范围。静态文档检查通过只支持文档层面的结论；模型性能、费用、正确率改善必须有另行取得的实验依据。
